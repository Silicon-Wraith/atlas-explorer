## What failed and what it means

The pre-hardware gate-r0 was intentionally stopped during CPU reference regeneration after source audit found incomplete delivery suppression. It records interruption and confirmed cleanup; no browser result existed. The preflight context-routing correction then failed in full gate-r1: page teardown delivered cancellation despite interception, so the held publication retired before expiry. The application did expire the pair, but that run could not establish the intended lost-token retirement cause.

The separately frozen137.316s diagnostic used a test-owned HTTP proxy. A native-free check confirmed forwarding, own-Origin/Host translation and exact-client suppression of all four operations. The replacement tab used the direct origin; production lease/backend/math were unchanged. This time the held publication retired inside expiry and both recoveries worked. However, the proxy returned503 to a renewal before the old page closed. The application correctly stopped that page and attempted retirement; the fixture deliberately refused its cancel/retire/final close, so it correctly emitted sticky `cleanup-error`. The suite's final prohibition on every cleanup-error across both pages then failed. The living page's deferred empty close and retry had succeeded; do not misattribute the old page's error to that recovery.

This is a fixture-definition mismatch: the lost-page scenario intentionally makes retirement acknowledgements impossible, while the aggregate assertion demands none fail. It is not permission to remove cleanup checks globally. A future correction must separate the intentionally disconnected old owner from the living/replacement owner and retain strict errors on the latter, with fault/cause timestamps. Alternatively a transport-level silent disconnect can avoid turning a synthetic503 into an early authoritative session refusal. Freeze and verify that choice before hardware. No third attempt was made here.
