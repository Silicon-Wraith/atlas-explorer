## Intended experience

Find a location in Plane, choose a supported mathematical-to-spatial interpretation, create its world definition, enter the prepared 3D landscape, explore structures at different scales, save the world/place and return. Support multiple saved world definitions and multiple source regions. Regression World serves validation requirements. Its content can change or be replaced as those requirements evolve; each result records the definition used. The existing specimen is the first migration control, not the product's sole landscape or a permanent freeze. Other fractal families can follow through explicit generator contracts; no universal conversion is assumed.

A source location/window and interpretation define mathematical content. A 3D viewpoint, observer body size, tessellation and cache state do not redefine it. Smaller-scale mathematical formations may use a new representation/topology, with compatible prepared collision. Appearance stays a separate domain. Whether a selected source window is an entry into a larger shared mathematical world or a distinct authored world definition must be explicit in the generator's construction; do not silently reseed while navigating.

## Execution sequence

1. **Trace and own the whole mechanism.** Complete the dependency graph from exact Plane/Mandelbrot source evaluation through parent-frame construction, descendant rules, sampling, mesh composition and preparation receipts. Separate mathematical source, canonical inputs, third-party dependencies, generated caches and experiment evidence. Source and reproducible input creation belong in the repository; generated outputs and evidence remain in scratch. Audit provenance/licenses before importing third-party code. Publish the design and freeze a small reviewed card before code migration.
2. **Migrate with the current world as a compatibility control.** Reconstruct the existing promised world through repository-owned source with fresh output/cache roots. Preserve old scene compatibility deliberately: its legacy identity includes historical paths, and source relocation can change code hashes and invalidate qualification certificates. Record aliases/version changes explicitly; do not carry an old certificate onto changed source. Verify geometry, render/collision consistency, opposite order/rebuild and the existing application route. This is source ownership, not proof of generalized creation or browser-only generation.
3. **Replace fixture inputs with a world recipe.** Define exact Mandelbrot source coordinates/window/scale, the numerical evaluation policy, versioned spatial interpretation and fixed feature/recursion lineage. Preserve Plane's decimal precision; do not round deep coordinates through Number. Separate the definition from generated meshes and per-observer requests. Determine which current assets can be regenerated and which must be explicit portable inputs. Bound supported sources and retain honest unsupported/unresolved results.
4. **Connect Plane to world creation and test real variation.** Add a supported entry from the current Plane location. Generate at least two meaningfully different, explicitly chosen source regions from the recipe rather than copied fixture meshes. Enter/move/contact, save/reopen and regenerate in different orders. Independently check their relationship to the named source mathematics. One successful fixture cannot qualify arbitrary sources, scales or topology.
5. **Resume interleaved AP1/MD2 experiences on that foundation.** Lighting/materials/controls and additional fixed-world formations can then improve real generated worlds. Keep mathematical detail generation, representation quality and shading evidence distinct. Production backend/reproducibility remains an explicit RB1 decision; owning native source does not select a production service or client implementation.

## Current definition and hosting questions

Today the native helper supplies a fixed definition from code, numeric parameters and input assets; the browser receives it and requests regions. The merged pre-migration path assembled it from scratch, while A1 loads an owned bundle and preserves the legacy definition literally. This is not yet a self-contained user-editable recipe or a Plane-to-world creation operation.

The advisor clarified that multi-user means a centrally hosted application serving independent users who can access/create worlds, not live multiplayer. Creation of the canonical definition, durable storage and geometry computation are separate choices. Central storage does not require central geometry generation. Client-side, service and hybrid preparation remain RB1 candidates; the owner discussed server registration/canonicalization as a possible future design, not an implemented or advisor-selected workflow. A2 must keep complete recipes and exact source coordinates independent of sessions, generated meshes and machine paths. RB1 must address user/world isolation, independent generation jobs and the current local helper's global one-tab limitation. No accounts, database, multiplayer or central service is added by A1.
