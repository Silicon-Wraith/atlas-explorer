## Experience and scope

If a Landscape tab disappears without closing its preparation client, the launcher eventually releases that client's publications. Another tab can then enter Landscape without restarting the helper. A second tab receives a clear already-in-use message while the owner is healthy. A living page that loses its lease stops input and preparation, retains its own in-memory pose, releases resources and offers an explicit retry. A delayed response from the old session cannot regain ownership or affect the replacement.

This is the planned A2 increment after PC3. Keep one preparation owner per launcher and the existing native control. Geometry, domain, D/D4 scales, math, sampling, speed and collision policy remain PC3's. Saved places/history are BI1.B; device/native restart parity is BI1.C. Surface sliding, navigation-limit feedback, new mathematical scales, tessellation and materials remain later interaction/AP1/MD2 work. The advisor's examples identify those later end-to-end cases and do not reorder this sequence. AP1/MD2 are interleaved workstreams with multiple future release cards; their complete scope is not frozen here.

## Audited gap and prior art

PC3's server has a single current runtime ID and explicit close, with bounded request/tombstone accounting. Without close, the ID stays current until launcher shutdown. Late request-identity retirement already protects a missing response token. However, browser cleanup requests from an expired client would currently fail the current-client check and could make local release appear unsuccessful. PC3's launcher also stops when its initial page closes even if another tab remains.

Use a conventional server lease and fenced client identity around those existing controls. Browser timers are advisory wakeups: [Page Visibility](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API) documents hidden-tab timer throttling and paused animation callbacks. [performance.now](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now#ticking_during_sleep) documents sleep differences and wall-clock adjustment limits. Context7 retrieved both on2026-10-30. A heartbeat interval is not proof of continued ownership; elapsed-time checks and server confirmation decide input eligibility. No new coordination service, browser-lock dependency or distributed-generation architecture is needed.

## Server lease and fencing

Production policy: **30,000 ms lease**, **5,000 ms heartbeat**, **1,000 ms expiry sweep**. Use an injected monotonic clock for server decisions; check expiry synchronously before every admission/renewal/native operation as well as during the sweep. Never extend a lease merely because a GET or a preparation response occurred. Timers may be late; an operation arriving at or after the deadline cannot revive the old owner. Real acceptance uses these production durations; fake clocks only accelerate CPU controls.

Bind an opaque per-client session nonce to the runtime ID before native initialization. The browser creates the nonce before open, so cancellation before learning metadata can still identify that opening. Native calls, renewal and close carry that pair. Neither public status nor normal event logs expose the nonce. The PC1 world/request/artifact wire formats and producer epoch semantics remain unchanged; the session fence belongs to the application transport.

Repeated open for the same current pair is idempotent. Another pair cannot take over, renew or close it. An expired/closed runtime cannot reopen; retry creates a new runtime and nonce. Retain bounded tombstones, including close-before-open, and reject new admission before accounting capacity becomes unsafe. A strictly increasing renewal sequence fences reordered requests; stale or repeated renewal cannot extend the deadline. A successful response reports policy and remaining duration, not a promise based on cross-context clock synchronization.

Expiry first invalidates the old identity, then aborts its transfers/queued requests and retires publications by complete request identity and token. Retirement failure is sticky: no new admission follows unconfirmed cleanup. A cancelled nonpreemptive native computation may finish while still owned by the launcher; it cannot publish to the expired client. Existing one-active/two-queued bounds and native deadlines remain. This does not claim immediate release of a frozen browser's GPU resources: the browser releases its owned resources when its event loop resumes, while resumed input remains fenced.

Closed clients may perform idempotent cleanup, scoped to their own recorded pair. A late retire/cancel/close acknowledges an already-retired old session without calling retirement on the current session's tokens. A stale prepare/buffer/heartbeat is rejected. Typed outcomes distinguish owned elsewhere (409), expired/closed (410), and unavailable or cleanup-failed (503). Origin/Host/JSON guards remain. Passive status never starts native work and reports availability without disclosing an owner capability.

## Browser lease and recovery

The application client owns renewal scheduling, one bounded renewal request at a time, and a conservative local deadline derived from request-send time plus the acknowledged remaining duration. A late response cannot move the deadline later merely because it arrived late; stale renewal generations are ignored. Use monotonic elapsed time and a wall-elapsed stall check so a long sleep/clock anomaly closes input conservatively rather than extending the local permit. Cross-host clock synchronization and arbitrary system-suspend correctness are not acceptance claims of this local control.

Before each navigation, prediction and scale action, check the lease gate synchronously. Heartbeat rejection, elapsed deadline or uncertain connection closes input immediately. A transient failed renewal can remain in a visibly paused checking state and retry within the unexpired permit; it cannot keep moving while verification is pending. Expiry invalidates the local request generation, suspends the runtime, terminates its worker and disposes the renderer through the existing release owner. Expected already-retired server cleanup is not a fabricated resource leak. Genuine cleanup failure remains sticky.

On hidden/blur, existing input clearing remains. On return from hidden, require a current server confirmation before accepting movement, even if the old timer has not fired. Do not rely on background timer frequency. Keep the last frame inert during checking/release. Session-status messages have priority over per-frame preparation messages and remain readable. A Retry Landscape action starts a fresh application session only after local cleanup; viewer and Plane remain reachable. Retry in the same living page uses its retained requested pose and current clearance. Another tab has its own requested state; PC4 does not transfer the abandoned tab's pose or add persistence.

## Launcher and ownership bounds

Track the launcher's owned context pages. Closing the initial page must not stop the helper while another owned page remains. Closing the last page, browser disconnection or terminal shutdown still stops the owned browser/server/native tree with existing bounded cleanup. Add a small testable page-lifetime owner rather than exposing a debug HTTP operation or changing the hardware profile.

Preserve all PC3 resource limits and native/source policy. Client retirement and local browser retirement are distinct observations. Report each independently; a server lease alone is not a GPU-memory measurement. Do not force a native process restart on ordinary expiry or silently reset a visitor to the origin.
