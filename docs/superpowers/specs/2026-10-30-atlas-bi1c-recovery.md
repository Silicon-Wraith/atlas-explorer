## Experience and risk

Explore Landscape and survive a lost GPU device without losing the mathematical place, requested file or histories. The first active-viewport device loss gets at most one automatic rebuild. A repeated loss, collision-worker failure or failed rebuild stops clearly and offers explicit Retry. An unavailable native preparer requires the Save-and-restart path described below. Retry rebuilds current compatible render/collision coverage and checks the current requested body's clearance before publishing or admitting input. A dead helper stops with a truthful restart reason. The living page can save its requested scene; a deliberate owned launcher/browser restart and actual file Open return to the same promised place. In-memory history is not serialized across that page restart.

The riskiest assumption is coordinated retirement: GPU, worker, native producer and user scene/history have different lifetimes. A fresh execution must not accept old receipts, cancel a new owner, silently reset the place, or start before old cleanup is confirmed. Loss during an unfinished restore must retain that newer request, rather than store the prior runtime pose over it.

## Audited gaps and API basis

Before BI1.C, rendering forwarded device loss and GPU errors as undifferentiated strings; worker errors could be invisible while idle; future native jobs could wait on a dead child; and known-loss queue rejection could obstruct resource retirement. The implementation now addresses those gaps. Existing generation, lease, file and history owners remain authoritative.

Current official WebGPU documentation was fetched with Context7 (`/gpuweb/gpuweb`). Uncaptured validation/OOM errors stop explicitly and never consume an automatic attempt. Device loss resolves device.lost, invalidates the device and its objects, and requires a fresh adapter/device for recovery. Deliberate destroy also loses the device; renderer disposal must suppress that intentional callback. The implementation must use a structured failure code and must not parse implementation-defined loss messages. [Specification](https://gpuweb.github.io/gpuweb/#dom-gpudevice-lost), [device destruction](https://gpuweb.github.io/gpuweb/#dom-gpudevice-destroy).

## Browser execution and policy

Keep recovery with the prepared workspace, not shared scene/history or the mathematical runtime. Use typed notifications from renderer and browser preparer. Every current failure synchronously closes input, settles accepted motion once, cancels scale/file work as applicable, invalidates the execution and starts tracked retirement. Old callbacks are ignored by state identity. GPU/worker handles never enter portable scenes.

- **First active-viewport device loss:** consume the one automatic recovery allowance and immediately request a fresh activation through the existing mode host. The host owns supersession/leave; do not schedule a later activation after an unrelated cleanup promise that could re-enter a departed workspace.
- **Repeated device loss or failed automatic rebuild:** stopped state with reason, Save/Open/Retry and Plane/viewer still available. No timed automatic loop. Ordinary leave/re-entry and scene edits do not replenish the allowance; explicit Retry does.
- **Worker crash, message failure, index deadline or other preparation error:** terminal preparer, reject pending work, stop visibly and require explicit Retry. No attempt to reuse a broken worker.
- **Failure before first presentation:** cancel unfinished execution and preserve the requested scene, then show unavailability/Retry through the existing fallback. Automatic recovery is reserved for an already active viewport. This boundary is explicit rather than claiming all startup-failure parity.
- **Retry:** reset the automatic allowance; restart the selected Landscape activation with fresh runtime/client/worker/device identity. Histories and requested scene are unchanged. An unsupported world/pose still fails admission. No silent scale, origin, sampling, speed or quality change.

The renderer records an execution epoch, reports device-loss separately from uncaptured GPU errors, rejects use after loss, and retires buffers on acknowledged device loss even if onSubmittedWorkDone rejects. Unrelated retirement errors remain sticky. Disposal always destroys owned resources and suppresses self-generated device-loss recovery. A consumer checks cancellation/terminal state across asynchronous physics initialization, worker completion and upload; late results are released, never published.

A pending scale intent is cancelled by interruption. Existing stale scale status is cleared on a fresh activation or accepted movement so it cannot hide the new recovery/frontier state. Imported roll's first-drag limitation is otherwise unchanged.

## Native preparation lifetime — r1 narrower boundary

Keep one adapter construction per server. An observed native process exit makes its adapter terminal; future jobs/reset fail promptly and new open/prepare/buffer/heartbeat admission returns a typed preparer-lost reason telling the visitor to save and restart ATLAS. Status stays passive. Cleanup/retire/cancel/close remain usable; no crash is mislabeled as lease expiry. Bind a client to its admitted adapter so late work and cleanup always reach that owner. Recheck terminal health after pending preparation/buffer reads and retire a late token before refusing it. Failed initialization stays a restart-required failure, with owned startup cleanup confirmed.

The living page retains world/request/pose/history. Save the actual file, confirm old owned browser/helper/server cleanup, start a fresh owned launcher/browser and Open that download; fresh producer identity and exact promised place are required. History stacks remain per-page in memory under BI1.B. No automatic helper process restart, hot-replacement owner, construction cap or multi-attempt output layout is added. Existing one-process/request/cache/residency/publication and4GiB successful-output quotas remain unchanged. Cleanup failure stays sticky. This narrower engineering boundary advances browser recovery without committing to native preparation as the release backend; RB1 owns that choice.

## Verification seams and scope

Use the existing diagnostic inspection precedent: an explicit device-destroy hook exercises an actual GPUDevice.lost; a diagnostic worker message throws an uncaught worker error, exercising the actual onerror path. These are inspection/test functions, not visitor controls. Native loss kills only the suite-owned, recorded helper PID while a preparation request is outstanding. Label this as process/request interruption, not proof of a particular GPU-kernel failure. No generic HTTP kill/restart endpoint is introduced.

Guarded CPU tests use real workspace/runtime logic with fake devices/workers/adapters and controlled promises. Cover one automatic attempt, repeated failure, explicit Retry, idle and pending worker loss, late callbacks/uploads, newer requested file winning, leave during recovery, current-pose clearance, sticky cleanup and no scene/history drift. Native controller controls check fail-fast exit and idempotent close with an injected fake child, without spawning processes. A native-free real HTTP replay exercises server terminal health, admission/tombstones and a held old completion after loss before hardware.

One headed recovery route records nondefault place/history, actual device destruction and automatic return; second destruction/stopped/explicit retry; actual worker error/explicit retry; actual owned helper exit/terminal stop, then saved-file return after full owned restart/new producer; input fences and unchanged requested place/history. CPU barriers establish precise races; the headed route is finite application evidence, not an arbitrary crash corpus. Existing application/contact/scale, file/history, session/launcher and Plane/viewer suites run in the final full gate on this source.
